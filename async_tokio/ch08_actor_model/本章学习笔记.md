# 第 8 章：Actor 模型 (The Actor Model) —— 学习笔记

本章介绍了 **Actor 模型**，这是一种通过消息传递来实现并发和状态管理的强大模式。Actor 是高度隔离的代码单元，非常适合构建模块化、可测试且容错性强的异步系统。

---

## 1. 核心概念与原理

### 1.1 什么是 Actor？

* **定义**：Actor 是一个独立的执行单元，它**仅通过消息传递**与其他部分通信。
* **特征**：
  * **隔离性**：每个 Actor 拥有私有的内部状态，外部无法直接访问或修改。
  * **顺序处理**：Actor 每次只处理一条消息（在单邮箱语义下），从而避免对内部状态的竞态；通常**无需在 Actor 内部**再套一层 `Mutex` 来保护同一邮箱串行处理的那段状态。

### 1.2 Actor vs Mutex（性能直觉）

`Mutex` 仍是保护共享数据的常用工具；在高竞争或特定负载下，**以邮箱串行化**的 Actor 有时能换来更可预测的延迟与更少的锁抖动。

* **锁开销**：争用 `Mutex` 时可能涉及阻塞、唤醒与缓存行乒乓。
* **通道优势**：Actor 常用 **mpsc** 等非阻塞邮箱排队；书中在特定基准（如 1 亿次操作）下对比了 Actor 与 `Mutex` 方案，**具体加速比以该书测试环境为准**。

---

## 2. 核心架构模式

### 2.1 路由模式 (The Router Pattern)

当系统中有多个不同功能的 Actor 时，可通过**路由 Actor** 统一分发消息。

* **消息布局**：使用嵌套的 `enum`（如 `RoutingMessage` 内含 `KeyValueMessage` 等）描述路由目标。
* **解耦**：调用方只持有路由器的 **`mpsc::Sender`**，不必知道后台 Actor 拓扑。

### 2.2 全局静态发送端

为避免在调用链上层层传递 `Sender`，可用 **`std::sync::OnceLock`**（或 `lazy_static` 等）保存全局 **`OnceLock<Sender<...>>`**，在启动时注入（书中如 `ROUTER_SENDER`）。注意：**初始化顺序与测试隔离**要自行设计，避免隐式全局耦合。

### 2.3 状态恢复 (State Recovery)

Actor 或进程重启后，可通过专门的 **Writer Actor** 将操作日志或快照落盘（如 `data.json`），再在启动时重放/加载，实现状态恢复。

---

## 3. Actor 监控与监督 (Supervision)

### 3.1 心跳机制 (Heartbeat)

为检测 Actor 是否存活，可定期向监督组件发送心跳；若超过阈值（如书中 **200ms**）未收到，可判定为疑似失效并进入恢复流程。

### 3.2 监督者模式 (Supervisor)

* **职责**：监控子 Actor / 任务的健康状态。
* **故障处理**：发现异常后，经路由器触发 **Reset**：中止旧任务、清理通道、重建 Actor 实例等，使系统具备**自愈**能力（具体策略：重启、退避、降级等由业务决定）。

---

## 4. 示例代码：处理响应的消息

在 Actor 模式中，若调用方需要拿回结果，常在消息里携带 **`oneshot::Sender`**：

```rust
use tokio::sync::{mpsc, oneshot};

struct RespMessage {
    value: i64,
    responder: oneshot::Sender<i64>,
}

async fn resp_actor(mut receiver: mpsc::Receiver<RespMessage>) {
    while let Some(msg) = receiver.recv().await {
        let result = msg.value + 1;
        let _ = msg.responder.send(result);
    }
}
```

---

## 5. 常见陷阱与注意事项 (Gotchas)

* **信道容量**：`mpsc::channel(cap)` 的 `cap` 要在**内存**与**背压**之间权衡；`0` 表示同步握手边界，大缓冲会掩盖上游过快问题。
* **死等心跳**：监听心跳或 `recv` 时应配合 **`tokio::time::timeout`**（或周期性 tick），否则可能长期阻塞导致监督误判或无法退出。
* **混合模式**：不必全栈 Actor；在现有 async 代码里，对**强状态边界**模块（缓存、会话、串行写盘）引入 Actor 往往性价比最高。

---

## 总结

第 8 章展示了 Actor 模型如何把并发复杂性收敛为**消息处理**。通过**路由器、心跳与监督**等组合，可以在部分组件故障时仍维持系统整体可用性（取决于你的恢复策略与持久化设计）。
