# 第 4 章：将网络集成到异步运行时 (Integrating Networking) —— 学习笔记

本章是全书中相对复杂的一章，重点在于如何在我们自定义的异步运行时中集成网络协议（如 HTTP），并深入到底层使用 **mio** 直接处理套接字（Sockets）。

---

## 1. 核心概念：执行器与连接器 (Executors & Connectors)

在异步网络编程中，理解这两个组件至关重要：

* **执行器 (Executor)**：负责将 Future 驱动至完成状态。它是运行时的一部分，负责调度任务并确保它们在就绪时运行。
* **连接器 (Connector)**：负责在应用程序和目标服务之间建立连接（例如打开 TCP 连接）并在请求生命周期内维护该连接。

---

## 2. 集成 hyper 库实现 HTTP 访问

虽然像 **hyper** 这样的库功能强大，但它通常默认依赖于 Tokio 运行时。要将其集成到自定义运行时中，需要完成以下步骤：

### 2.1 自定义执行器

需要为自定义运行时实现 `hyper::rt::Executor` trait，以便 `hyper` 能够使用我们的调度逻辑来执行任务。

### 2.2 自定义异步连接器

由于 `hyper` 默认预期 Tokio 管理连接，我们需要构建一个独立的异步连接器。

* **支持 HTTP 与 HTTPS**：通过定义 `CustomStream` 枚举来处理普通的 **TcpStream** (HTTP) 和封装了 TLS 层的 **TlsStream** (HTTPS)。
* **实现 IO Trait**：书中为与 `hyper` 对接，往往需为自定义流实现 `tokio::io::AsyncRead` / `AsyncWrite`（或随 `hyper` 版本选用其要求的 IO 抽象），在 `poll_read` / `poll_write` 中把底层就绪与 **Waker** 联系起来。

---

## 3. 深入底层：使用 mio 处理底层 I/O

**mio** 是 Rust 中常用的**跨平台、非阻塞 I/O** 原语库（基于 epoll / kqueue / IOCP 等），许多高层运行时（如 Tokio）在其之上构建。

> 说明：坊间有时把 mio 说成「Metal I/O」；**官方 crate 名就是 *mio***，把它记成「贴近金属的 I/O」无妨，但不必当成正式全称。

### 3.1 令牌机制 (Tokens)

`mio` 旨在同时处理成千上万个套接字。为了识别是哪个套接字触发了事件，它使用了 **Token**（对 `usize` 的封装）。

* **流程**：注册套接字 → 等待就绪 → 根据 Token 查找状态 → 执行操作 → 重复。

### 3.2 轮询套接字 Future

通过手动实现一个 `ServerFuture`，我们可以利用 `mio::Poll` 来轮询套接字并在数据到达时通过 **Waker** 唤醒 Future。

* **非阻塞读取**：在循环中不断从套接字读取数据到缓冲区，直到 `WouldBlock` 或没有更多字节为止。

---

## 4. 关键依赖项

* **`hyper`**：快速的 HTTP 实现；与自定义运行时对接时需按需开启特性（如 `client`），并自行桥接 `Executor` / IO。
* **`mio`**：底层非阻塞 OS 抽象；常用特性包括 `net`、`os-poll`（按目标平台查阅文档）。
* **`async-native-tls`**：异步 TLS 的一种选项（与具体运行时组合使用）。
* **`smol`**：小型异步运行时，可作轻量任务或对照阅读。

---

## 5. 易错点与建议 (Gotchas)

* **复杂性警告**：本章被作者认为是全书最难的部分。如果你不打算构建自定义的网络运行时，可以先跳过并在阅读完后续章节后再回来复习。
* **标准端口**：HTTP 默认使用 80 端口，而 HTTPS 使用 443 端口。
* **零成本抽象**：`mio` 以 **Token** 区分事件源，避免回调风格，便于在其上搭建 Future / 流式抽象。
* **生产环境建议**：虽然本章展示了如何从底层构建服务器，但对于生产环境，建议使用成熟的 **Tokio + hyper/axum** 等方案，而不是仅停留在教育性质的底层拼装。

---

## 总结

第 4 章展示了异步运行时如何与操作系统底层的网络能力交互。通过实现自定义的 **Executor** 和 **Connector**，你可以让原本绑定在特定框架下的库运行在你自己的引擎上。
