# 第 1 章：异步编程入门 —— 深度解析版

本章目标：帮你跨过**硬件现实**与**软件写法**之间的鸿沟——为什么多核时代仍要异步、**进程 / 线程 / 异步任务**各解决什么问题。

对有 Rust 基础的新手，先记住一句总纲：

> **异步不是为了让 CPU「算得更快」，而是为了在等 I/O 时别让 CPU（和线程）闲着。**

下面按书中小节 **1.1～1.6** 展开；文末有与本仓库示例的对应。

---

## 1.1 什么是异步？ (What Is Async?)

### 核心背景：摩尔定律的放缓

过去「算法慢了就换颗更强的 CPU」还能扛一阵；如今单核性能爬升变慢，**堆核**也不便宜。与此同时，微服务、网关、数据库代理里充斥着 **网络 I/O**：等的时间往往远大于算的时间。

### 异步的本质：利用「死时间」(Dead Time)

* **同步心智**：烧水时**站在水壶边死等**（线程/进程在等），别的活干不了。
* **异步心智**：按下烧水开关后**立刻**去切菜、回邮件；水开的这段时间就是 **Dead Time**，被用来推进别的工作。
* **结论**：异步让程序在等网络、磁盘、外设时**仍能推进别的工作**，从而在**不线性增加 CPU 核心**的前提下，提高**吞吐与响应性**（总延迟是否下降，取决于 workload 是否 I/O 主导）。

---

## 1.2 进程简介 (Introduction to Processes)

### 操作系统里的「大盒子」

* **资源单位**：进程是 OS **分配资源**的边界，拥有独立虚拟地址空间（自己的栈、堆等）。
* **隔离性**：一个进程崩溃，通常不会直接踩烂另一个进程的内存——在 C/C++ 时代这是很重要的安全边界。

### 代价：贵与慢

* **创建昂贵**：新建进程要分配页表、句柄、初始化大量内核结构。
* **IPC**：进程间**不能**像同进程线程那样直接共享一块用户态内存；跨边界传数据往往要**序列化 + 内核中转**，延迟与工程复杂度都高。

### 和 Rust 的关系

Rust 的内存安全主要解决**同一地址空间内**的数据竞争；**多进程**仍是可选部署模型，但日常异步服务端更常见的是**单进程多线程 + async 运行时**。

---

## 1.3 什么是线程？ (What Are Threads?)

### 进程内的「舞者」

* **调度单位**：线程是 OS 调度的常见**最小执行序列**；一个进程可挂多个线程。
* **共享地址空间**：同进程线程共享内存——传 **`Arc<T>`** 比跨进程 IPC 轻量得多。

### 共享的代价

多线程可同时改同一数据 → 需要 **`Mutex`**、**原子类型** 或消息传递等纪律，否则会出现 **Data Race**（Rust 编译器会拦一部分，逻辑层仍要你自己设计）。

### 上下文切换 (Context Switching)

从线程 A 切到线程 B 要保存/恢复寄存器、缓存局部性变差；线程**极多**时，切换本身会变成显著开销。异步的意义之一，是在**少量 OS 线程**上 multiplex 大量「等 I/O」的任务，减少「为等而开线程」的浪费。

---

## 1.4 异步的应用场景 (Where to Utilize Async?)

### I/O 边界 vs CPU 边界

* **CPU-bound（算力型）**：加密、转码、大规模数值模拟——主要靠**更多核 / SIMD / 更好算法**；单纯套一层 async **不会魔法加速**。
* **I/O-bound（等型）**：读盘、打 HTTP、等用户输入——大量时间在**等**。

### 数量级直觉

访问 DRAM 常在 **~100ns** 量级；一次网络 RTT 常在 **~1ms～100ms+**。中间差 **约 10⁴～10⁶ 倍**：在这段「空窗」里，CPU 本可以执行大量指令；异步的目标就是**把空窗用起来**，而不是让线程在空窗上干等。

---

## 1.5 使用异步进行文件 I/O (Async for File I/O)

### 常见误区

**异步不会让磁盘物理读写得更快**——带宽与延迟由介质与总线决定。

* **真正收益**：大块读写或慢盘时，**别卡住** UI 线程、别堵住 Web 服务器里别的请求——主循环/执行器仍能调度其他任务。

### Rust / OS 的现实

不少平台上 **`tokio::fs`** 等会在底层用**线程池**去「模拟」非阻塞体验，并不等价于「每个 read 都是内核真·异步」。Linux 上更彻底的路线常涉及 **`io_uring`**（及生态如 **`tokio-uring`**），需单独评估与运维成本。

### 与 `sleep` 的关系

在「轮询文件元数据」这类循环里，必须用 **`tokio::time::sleep`**，不能用 **`std::thread::sleep`**（见下文「不要阻塞执行器」）。

---

## 1.6 利用异步提升 HTTP 请求性能

### `tokio::join!` 在干什么？

假设 4 个请求各自 RTT 约 **150ms**（教学用数字，以你实测为准）：

1. **顺序同步**：150 + 150 + 150 + 150 ≈ **600ms**。
2. **`tokio::join!` 并发**：四个 Future 同时挂出去，总墙钟时间通常接近 **最慢那一个**（仍约 **150ms** 量级，而非相加）。

### 性能倍数

书中常给出约 **4.7×** 一类对比——**仅作数量级示意**；真实倍率取决于 RTT 分布、DNS、TLS、连接复用、目标服务限速等。

### 书内示例：`tokio::join!` + `reqwest`

```rust
use std::time::Instant;
use reqwest::Error;

#[tokio::main]
async fn main() -> Result<(), Error> {
    let url = "https://jsonplaceholder.typicode.com/posts/1";
    let start_time = Instant::now();

    let (_, _, _, _) = tokio::join!(
        reqwest::get(url),
        reqwest::get(url),
        reqwest::get(url),
        reqwest::get(url),
    );

    println!("并发请求总耗时: {} ms", start_time.elapsed().as_millis());
    Ok(())
}
```

## 核心警告：不要阻塞执行器 (Don't Block the Executor)

这是第一章里最需要带进第二章、以后每一章的**实战守则**。

* **错误**：在 `async` 任务里调用 **`std::thread::sleep`**（或其它长时间**阻塞**的同步 API：同步文件读大文件、死锁式 `Mutex` 等）。
* **后果**：阻塞的是跑 `poll` 的 **OS 线程**。工作线程池若很小（例如 4），几条路径一起睡，就可能把**整站吞吐**拖垮——不是「某一个请求慢」，而是**全局停顿感**。
* **正确**：等待时间用 **`tokio::time::sleep`** 等「返回 `Pending`、把线程还给调度器」的 API；真正重的阻塞工作考虑 **`spawn_blocking`** 或独立线程，并限制并发。

---

## 章节小结

第一章用进程 / 线程 / I/O 时间尺度把问题说清楚：**异步的使命是高效管理「等待」**——在 **I/O-bound** 场景用 async 模型换吞吐与响应；同时**认清边界**，别把 CPU-bound 误当成能靠 async 解决的问题，并**永远避免在异步执行路径上阻塞线程**。
