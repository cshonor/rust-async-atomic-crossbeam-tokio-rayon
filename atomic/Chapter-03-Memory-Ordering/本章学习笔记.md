## 1. 为什么需要内存顺序？

现代 CPU 与编译器为性能会做 **指令重排（Instruction Reordering）**。若对共享数据并发访问却不加约束，各线程看到的**有效顺序**可能与源码不一致。

- **内存模型（Memory Model）**：Rust（继承 C++）用抽象模型统一 x86、ARM 等架构。  
- **核心关系**：**Happens-Before（发生于…之前）** — 定义跨线程的「谁先谁后」。  
- **`Ordering`**：向编译器与 CPU 下达的**重排限制**；每个原子操作都必须显式传入。

> **原子性**消除该原子变量上的**数据竞争**；**Ordering** 解决**其他内存**的可见性与顺序。

## 2. 五大内存顺序（精读）

### ① `Ordering::Relaxed`（宽松）

| 项 | 内容 |
|----|------|
| **保证** | **无**跨线程 HB；仅同一原子变量的 **总修改顺序（Total Modification Order）** |
| **效果** | 可重排该操作与其他变量；他线程可能先看到原子更新，仍看不到此前对普通内存的写 |
| **场景** | 独立计数器、唯一 ID、与「别内存就绪」无关的统计 |

### ② `Release`（释放）与 ③ `Acquire`（获取）

**必须成对** — 并发通信的「工作马」。

| | Release | Acquire |
|---|---------|---------|
| **用于** | **Store**（及 RMW 的写侧） | **Load**（及 RMW 的读侧） |
| **屏障** | 前面的内存操作**不能**排到它**之后** | 后面的内存操作**不能**排到它**之前** |
| **HB** | A：`Release` store → B：`Acquire` load **读到该写入** → A 在 Release **之前**的写对 B 在 Acquire **之后**可见 |

**场景**：消息传递、**互斥锁 / 自旋锁**（先写数据，再 Release 标志；读标志用 Acquire，再读数据）。

→ 代码：``../Chapter-02-Atomics/2.2-load-store/2.2-load-store-demo.rs``；**第 4 章**：[4.1-spin-lock/4.1-spin-lock-demo.rs](../Chapter-04-Spin-Locks/4.1-spin-lock/4.1-spin-lock-demo.rs)

### ④ `Ordering::AcqRel`（获取并释放）

| 项 | 内容 |
|----|------|
| **用于** | **RMW**（`fetch_add`、`compare_exchange`、`swap` 等） |
| **语义** | 读侧 **Acquire** + 写侧 **Release** 合一 |
| **场景** | 单次原子操作既要「看见之前发布」又要「向后续发布」 |

### ⑤ `Ordering::SeqCst`（顺序一致）

| 项 | 内容 |
|----|------|
| **保证** | 含 Acquire/Release 约束 + 所有 **SeqCst** 操作共有一条 **全局严格总顺序** |
| **效果** | 所有线程对 SeqCst 操作看到**同一条时间线** |
| **场景** | **极少** — 如书中「双旗帜」：线程需根据**两个不同原子**写入的**全局先后**做决策 |
| **审查** | 代码里大量 SeqCst 常是**警告信号**（未分析清需求或偷懒） |

### 对照表（必背）

| Ordering | 跨线程 HB | 典型 |
|----------|-----------|------|
| Relaxed | 无 | 独立计数 |
| Release | 与配对 Acquire | 发布 / 解锁 |
| Acquire | 读到 Release 后 | 订阅 / 加锁 |
| AcqRel | RMW 双向 | fetch/CAS/swap 当信使 |
| SeqCst | 全局 SeqCst 顺序 | 多原子全局先后决策 |

## 3. 选型原则（从弱到强）

1. **首选 Relaxed** — 只更新单变量、不传「别数据已就绪」。  
2. **默认 Acquire / Release** — 标志位、锁、信道式同步：写 **Release**，读 **Acquire**。  
3. **RMW 当同步点** — 考虑 **AcqRel**。  
4. **极度谨慎 SeqCst** — 先证明 RA 不够；ARM 上还有额外成本。

```text
  信使原子同步普通内存？ → 禁止 Relaxed，用 Release/Acquire（或 AcqRel 的 RMW）
  仅单变量统计？ → Relaxed
  多原子全局时间线？ → 才考虑 SeqCst
```

---

## 4. 新手易错点与核心认知

| 误区 | 正解 |
|------|------|
| Relaxed = 更新「更慢」 | 模型规定**顺序**不规定**时间**；快慢看缓存一致性，与 Ordering 无简单对应 |
| x86 不乱序就不用 Ordering | **编译器仍可重排**；错 Ordering 会生成错误机器码 |
| SeqCst 万能最安全 | 多数场景 RA 足够；SeqCst 掩盖分析、损性能 |
| Relaxed 当「数据就绪」标志 | 必须 Release + Acquire |

（与第 2 章衔接：`fetch_add` 回绕、CAS 用 `compare_exchange_weak` — 见 `../Chapter-02-Atomics/2.4-cas/2.4-cas-id-allocator-demo.rs`。）

## 6. 面试一句话

**Ordering 用 HB 约束重排：Relaxed 只保单原子总序；Release/Acquire 同步普通内存；AcqRel 用于 RMW；SeqCst 全局最严极少用；锁与标志用 Acquire 加锁、Release 解锁。**

## 7. 极简背诵卡

| # | 背这句 |
|---|--------|
| 1 | 重排+内存模型；Ordering 定义 HB，每原子操作必传。 |
| 2 | Relaxed：无 HB，单原子总修改顺序；独立计数用。 |
| 3 | Release：前序写不能排到 store 后；用于发布/解锁。 |
| 4 | Acquire：后续读不能排到 load 前；读到 Release 见之前写。 |
| 5 | AcqRel：RMW 读 Acquire+写 Release。 |
| 6 | SeqCst：全局一致顺序；多原子先后决策才考虑。 |
| 7 | 选型弱→强；信使禁 Relaxed；x86 也要防编译器重排。 |
| 8 | 第 4 章自旋锁：lock=Acquire swap，unlock=Release store。 |
