## 1.8 Waiting: Parking and Condition Variables（Park 与条件变量）

> 书 §1.8 · 承接 [1.7 Mutex](./1.7-mutex-rwlock.md) · 深度笔记：[Condvar与条件变量-贯通笔记.md](../Condvar与条件变量-贯通笔记.md)

---

## 一、为什么需要「等」

`Mutex` 解决**互斥**（同时只有一个线程改数据），但不解决**协调**：

- 消费者发现队列**空**，不能一直占着锁空转；
- 生产者入队后，要**通知**正在等的消费者。

两类工具：

| 工具 | 层级 | 典型用途 |
|------|------|----------|
| **`thread::park` / `unpark`** | 线程休眠 / 唤醒 | 简单一对一通知 |
| **`Condvar` + `Mutex`** | 条件等待 + 互斥 | 生产者-消费者、线程池 |

---

## 二、`thread::park` 与 `Thread::unpark`

### 基本语义

- **`thread::park()`**：当前线程休眠，直到被 **`unpark`** 或（带超时 API 时）超时。
- **`thread::current().unpark()`** 或保存的 **`Thread`** 句柄上调用 **`unpark()`**。

### 关键：`unpark` 先于 `park` 不丢信号

若 **`unpark` 在 `park` 之前**调用，信号**不会丢失**——下次 `park` **立即返回**（「permits」模型）。

```rust
use std::thread;
use std::time::Duration;

let t = thread::current();
thread::spawn(move || {
    thread::sleep(Duration::from_millis(100));
    t.unpark();
});
thread::park(); // 可能被提前 unpark，也可能在这里睡
```

### 局限

- 适合**简单**暂停 / 恢复；
- **多生产者 / 多消费者**下很难精准唤醒「在等某一个条件」的特定线程；
- 与共享状态配合时，自己处理「检查条件 + 睡眠」易出竞态 → 用 **`Condvar`**。

仓库对应：Demo `demo_park_timeout`、`demo_wait_vs_park`

## 三、`Condvar` 基本模式

**必须与 `Mutex` 绑定**。典型结构：

```rust
use std::sync::{Condvar, Mutex};
use std::collections::VecDeque;

struct Queue {
    inner: Mutex<VecDeque<u32>>,
    not_empty: Condvar,
}
```

### 消费者：`while` + `wait`

```rust
let mut q = queue.inner.lock().unwrap();
while q.is_empty() {
    q = queue.not_empty.wait(q).unwrap();
}
let item = q.pop_front().unwrap();
drop(q); // 尽早放锁再处理 item
```

**`wait(guard)` 原子地**：

1. **释放** `Mutex`；
2. 线程休眠；
3. 被唤醒后 **重新加锁**，返回新的 `MutexGuard`。

→ 避免「先 unlock 再 sleep 之间丢通知」的竞态。

### 生产者：`notify`

```rust
{
    let mut q = queue.inner.lock().unwrap();
    q.push_back(item);
}
queue.not_empty.notify_one(); // 或 notify_all()
```

仓库对应：[1.8-parking-condvar-demo.rs](./1.8-parking-condvar/1.8-parking-condvar-demo.rs) — `demo_condvar_basic`

## 四、虚假唤醒（Spurious Wake-up）

**`park` / `Condvar::wait` 可能在没有明确信号时也苏醒** → 条件检查必须在 **`while` / `loop`** 里，**不能**单独 `if`：

```rust
// ✅
while q.is_empty() {
    q = cv.wait(q).unwrap();
}

// ❌ 唤醒后队列可能仍空
if q.is_empty() {
    q = cv.wait(q).unwrap();
}
```

---

## 五、`notify_one` vs `notify_all`

| 方法 | 行为 | 场景 |
|------|------|------|
| **`notify_one()`** | 唤醒**一个**等待线程 | 单消费者、单条件 |
| **`notify_all()`** | 唤醒**全部**等待者 | 多条件、广播、避免漏唤醒 |

被唤醒的线程仍须**重新检查条件**（可能多个线程同时被唤醒，或条件尚未满足）。

仓库对应：`demo_notify_methods`

## 六、超时 API

| API | 作用 |
|-----|------|
| **`Condvar::wait_timeout`** | 条件不满足时最多等一段时间；返回 `(guard, WaitTimeoutResult)` |
| **`thread::park_timeout`** | 线程休眠上限；可被提前 `unpark` |

超时后应像正常唤醒一样**再查条件**，不要假设一定就绪。

仓库对应：`demo_wait_timeout`、`demo_park_timeout`

---

## 七、主动 `drop(guard)` 再干慢活

消费者从队列取出任务后，**处理任务可能很慢**——应 **`drop(q)` 释放锁**，再 `sleep` / 计算，否则生产者无法入队。

仓库对应：`demo_active_drop`

---

## 八、对照：`park` vs `Condvar::wait`

| | **`thread::park`** | **`Condvar::wait`** |
|---|-------------------|---------------------|
| 依赖锁 | 否 | **必须**持 `MutexGuard` 传入 |
| 释放锁 | 不涉及 | wait 时**自动释放**，醒后**重新加锁** |
| 条件变量 | 无；自己管状态 | 与 `Mutex` 保护的数据配合 |
| 丢通知 | `unpark` 可先于 `park` | `wait` 与 `notify` 成对设计防竞态 |
| 典型场景 | 线程池 worker 简单挂起 | 生产者-消费者、任务队列 |

---

## 九、新手易错

1. **`if` 代替 `while` 等条件** → 虚假唤醒导致逻辑错误。
2. **持锁做耗时处理** → 吞吐骤降；取出数据后立刻 `drop(guard)`。
3. **`notify` 时仍持锁**（通常可以，但别在持锁时做重活）；更糟的是**忘了 notify**。
4. **用 `park` 实现复杂队列** → 状态与唤醒难配对；用 `Condvar`。
