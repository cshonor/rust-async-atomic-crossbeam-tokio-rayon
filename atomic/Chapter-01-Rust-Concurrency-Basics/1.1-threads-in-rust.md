## 1.1 Threads in Rust（Rust 中的线程）

> 书 §1.1 · 作用域线程完整版见 [1.2 Scoped Threads](./1.2-scoped-threads.md)

---

## 一、进程与线程通俗理解

1. **进程**：每一个独立运行的软件程序，各自拥有独立内存空间，进程之间天然隔离，没法直接互相读写数据，想要通信要依靠操作系统提供的特殊接口。
2. **线程**：依附在进程内部，**同一个进程里所有线程共用同一份内存空间**，这是多线程之间可以共享数据的根本原因。操作系统依靠高速切换 CPU 执行流，实现多个线程看似同时运行的效果。

Rust 不靠操作系统限制共享内存出错，而是**在编译阶段借助所有权、借用规则**，从语法层面阻止多线程非法争抢内存，规避数据损坏问题。

---

## 二、主线程生命周期关键规则

1. 程序从 `main` 函数所在的主线程启动。
2. **主线程执行完毕、函数 return，整个进程直接结束**，所有还在运行的子线程会被操作系统强制终止，不会等待子线程执行完。
3. `thread::spawn` 创建线程后会返回 `JoinHandle` 类型的值：
   - 调用 `handle.join()`：主线程暂停卡住，阻塞等待对应子线程运行结束之后，主线程才会继续向下执行；
   - 子线程正常运行结束：`join()` 返回 `Ok(子线程返回值)`；
   - 子线程运行中 panic 崩溃：`join()` 返回 `Err`，内部携带 panic 相关报错信息，主线程可以捕获这个异常。

示例最简代码：

```rust
use std::thread;

fn main() {
    let jh = thread::spawn(|| {
        println!("子线程正在运行");
    });
    // 主线程阻塞，等待子线程结束
    let _ = jh.join();
    println!("主线程收尾");
}
```

仓库对应：[1.1-threads-in-rust-join-demo.rs](./1.1-threads-in-rust/1.1-threads-in-rust-join-demo.rs)

### 逐行导读

```rust
use std::thread;           // 标准库线程模块

fn main() {
    // spawn：闭包 = 子线程入口；返回 JoinHandle<()>
    let jh = thread::spawn(|| {
        println!("子线程正在运行");
    });

    // join：阻塞**当前**线程，直到 jh 对应子线程结束
    let _ = jh.join();       // Result<(), Box<dyn Any + Send + 'static>>

    println!("主线程收尾");
}
```

### 运行结果（有 `join` 时顺序固定）

```text
子线程正在运行
主线程收尾
```

### 去掉 `join()` 的两种现象

**仅 `println!`、无 sleep**——与主线程**竞态**，输出**不保证**：

```rust
thread::spawn(|| println!("子线程正在运行"));
println!("主线程收尾");
// 有时两行都有，有时只剩「主线程收尾」
```

**子线程 `sleep` 很久、`main` 立刻 return**——子线程几乎必被强杀（见 JoinHandle §4）。

### 补充

- Rust 默认 **`std::thread` = OS 原生线程**，不是 green thread / 协程；轻量并发见 [§六 tokio::spawn](#六对照stdthreadspawn-vs-tokiospawn)。
- 闭包若要**捕获**外部变量，须满足 **`Send + 'static`**（常写 `move`）→ [JoinHandle 精读](#joinhandlet-精读spawn-返回值) · [1.2 scope](./1.2-scoped-threads.md)。

## JoinHandle\<T\> 精读（`spawn` 返回值）

**一句话结论**：`std::thread::spawn(闭包)` → 返回 **`JoinHandle<T>`**，`T` = 子线程闭包的**返回值类型**。

```rust
use std::thread;

fn main() {
    let h = thread::spawn(|| {
        println!("子线程正在运行");
        100 // 子线程返回值 → JoinHandle<i32>
    });

    let res = h.join().unwrap();
    println!("子线程返回值：{res}");
    println!("主线程收尾");
}
```

```text
子线程正在运行
子线程返回值：100
主线程收尾
```

仓库对应：[1.1-threads-in-rust-return-demo.rs](./1.1-threads-in-rust/1.1-threads-in-rust-return-demo.rs)

### 1. JoinHandle 是什么

1. **持有对应子线程的 join 权**（句柄，非线程本体）；另有 **`.thread()`** 可查 `ThreadId`，**同步等待靠 `join()`**。
2. **`.join()`**：阻塞**当前**线程，等待子线程执行完毕，取回返回值：
   - 线程正常结束 → `Ok(返回值)`
   - 子线程 panic 崩溃 → `Err(崩溃信息)`（panic 载荷）
3. **不调用 `join`、也不 drop 这个变量**：`main` 结束时进程退出，**子线程会被强制终止**（见下「不用 join」）。

> 补充：若 **`drop` 了 `JoinHandle` 且未 `join`**，子线程变为 **detached**，与 caller 脱钩；`main` 退出时同样可能来不及跑完。

### 2. 类型拆解

```rust
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
```

| 泛型 | 含义 |
|------|------|
| `F` | 传入的线程函数 / 闭包 |
| `T` | 线程函数返回值 → 就是 `JoinHandle<T>` 里的泛型 |
| `Send + 'static` | **闭包捕获的变量必须能跨线程转移所有权**，不能借用栈上临时变量 |

### 3. 关键易错点

```rust
// 错误：借用 &s，不满足 'static
let s = String::from("xxx");
let h = thread::spawn(|| &s); // 编译不过
```

> `spawn` 要求捕获值**所有权转移进子线程**（通常写 `move`），不能随便借用主线程局部变量。要借局部数据 → [1.2 scope](./1.2-scoped-threads.md)。

### 4. 不用 join 会怎样？

```rust
thread::spawn(|| {
    std::thread::sleep(std::time::Duration::from_secs(5));
    println!("子线程");
});
// main 立刻退出 → 子线程直接被杀 → 上面 println 不会执行
```

与 **`tokio::spawn`（异步 task 的 `JoinHandle`）** 的对照见下文 [§六](#六对照stdthreadspawn-vs-tokiospawn)。

### 5. 两个易混点（先纠正）

1. **`JoinHandle` 不只有 `join()`**：还有 **`.thread()`** → 拿到 **`&Thread`**（查 `ThreadId`、调试）；**唯一带同步语义、用来「等子线程结束」的核心 API 仍是 `join`**。
2. **`JoinHandle` 不是「线程本体」**：它是**创建者持有的句柄**，用来和后台 **OS 线程**做「等待 + 取返回值 + 回收内核资源」；真正的执行体在另一条内核线程里。

### 6. 底层原理：OS → 标准库 → `join()`（三层）

#### （1）OS：原生线程与 `pthread_join`

`thread::spawn` 最终会创建 **pthread**（Linux/macOS）或 **CreateThread**（Windows）：

| 概念 | 说明 |
|------|------|
| 线程对象 | 独立栈、PC、调度实体 |
| 状态 | 运行 / 就绪 / 阻塞 / 终止 |
| 未 join 的已结束线程（Unix） | 可能暂存为 **僵尸线程**，直到有人 `join` 回收退出状态 |
| **`pthread_join` / `WaitForSingleObject`** | 目标还在跑 → **调用线程进内核阻塞**；目标结束 → 唤醒调用者，返回退出信息并回收 |

**OS 一句话**：`join` 是内核提供的 **「等另一个线程结束」** 阻塞原语。Rust 的 `JoinHandle::join()` 是对这套调用的**安全封装**（并加上 panic 传播、返回值 `T`）。

#### （2）标准库实装 vs 教学心智模型

下面这套 **`Arc` + `Mutex` + `Condvar` + `AtomicBool`** 是**帮助理解「阻塞 / 唤醒」的心智模型**，**不是** `library/std` 在 Linux 上的逐行源码——在 Unix 上 **`join()` 通常直接 `pthread_join` 原生句柄**，阻塞主要发生在**内核**，而不是 Rust 再套一层用户态条件变量。

```rust
// ⚠ 教学简化伪代码，非 std 源码
pub struct JoinHandle<T> {
    native: NativeThread,     // OS 线程句柄
    sync: Arc<ThreadSync>,    // 与子线程共享的完成状态（概念上）
    // … 返回值 / panic 载荷由 std 内部协议传回 …
}

struct ThreadSync {
    finished: AtomicBool,
    cond: Condvar,
    mutex: Mutex<()>,
}
```

**spawn 时**（概念上）：创建者与**子线程**各持有一份对「完成状态 / 结果通道」的引用，以便子线程结束时把 **`T` 或 panic** 交回给 `join()`。

**读源码时**：看 `library/std/src/thread/` 下各平台的 `join` 与 `Packet`/`Thread` 封装即可；本节重点记 **OS join 语义**，不必背伪代码字段名。

#### （3）`join(self)` 在语义上做了什么

调用 **`jh.join()`** 时（与 [1.8 Condvar](./1.8-parking-condvar.md) 对照理解）：

1. **阻塞当前线程**，直到目标子线程**自然跑完**（或 panic 结束）；
2. 子线程结束时，std 把 **返回值** 或 **panic 载荷** 交给 `join` 的调用者；
3. **`join` 消耗 `self`**（见下），回收与「可 join」相关的资源；Unix 上同时完成 **`pthread_join` 式回收**。

用户态 Condvar 模型下的三步（**语义等价**，便于和 §1.8 联想）：

| 步骤 | 等待方（调 `join` 的线程） | 子线程结束路径 |
|------|------------------------------|----------------|
| 1 | 见未完成 → **阻塞**（内核 join 或等价 wait） | 继续跑闭包 |
| 2 | — | 写完成标记 / 结果，**唤醒**等待方 |
| 3 | 被唤醒 → 取 `Result<T, _>`，继续执行 | 线程终止 |

### 7. 为什么对外几乎只暴露 `join`？

| 原因 | 说明 |
|------|------|
| **所有权：只能 join 一次** | `join(self)` 消耗 `JoinHandle`；OS 上重复 join 是 UB → Rust 用类型系统静态禁止 |
| **职责单一** | `spawn` 负责**启动**；`JoinHandle` 负责**等待 + 回收 + 取返回值** |
| **刻意不提供 kill/suspend** | 强杀线程可能破坏锁、内存安全 → 标准库只鼓励 **等其自然结束** |
| **跨平台** | Windows / pthread 细节不同，对外统一成 `join()` |

```rust
pub fn join(self) -> Result<T, Box<dyn Any + Send + 'static>>
//     ^^^^ 消耗 handle，不能 jh.join(); jh.join();
```

### 8. drop 而不 `join` 会怎样？

| 行为 | 后果 |
|------|------|
| **`drop(JoinHandle)` 且未 join** | 线程 **detach**（与 handle 脱钩）；**不会**在 drop 时阻塞 |
| 子线程仍在跑 | 继续执行，但**无法再 `join` 取返回值** |
| **`main` / 进程退出** | OS **强杀**未结束线程；子线程收尾逻辑可能来不及跑 |

`join` 本质是 **同步屏障**：保证「子线程完整跑完（或 panic 被取回）」再让等待方继续。与 §二「去掉 join」、§4 sleep 示例一致。

### 9. 极简总结

1. **内核**：`join` = 等另一线程结束的内阻塞原语（`pthread_join` / `WaitForSingleObject`）。  
2. **句柄**：`JoinHandle` = 创建者侧的同步 + 取结果对象，不是线程本身；另有 **`.thread()`** 仅查询。  
3. **`join()`**：阻塞 → 取 `Result<T, _>` → 消耗 handle，只能一次。  
4. **Condvar 伪代码**：理解阻塞/唤醒用；**Unix 实装以 OS join 为主**。

## 三、ThreadId

操作系统配合标准库自动为每一个运行的线程分配唯一的 ID 编号。

- **作用**：只用于日志打印、区分不同线程，支持等值对比；
- **限制**：编号不一定连续生成，无法通过 ID 实现关闭、操控线程。

## 四、三种创建线程方式（重点：Builder、scope 预览）

### 1. 最简创建：`thread::spawn`

语法要求：传入的闭包必须满足 `'static` 生命周期约束。

> **通俗解释**：闭包捕获的变量，所有权必须完整转移到子线程中，不能借用主线程栈上临时变量，因此日常使用基本都搭配 `move` 关键字，把外部变量所有权移入闭包。

示例：

```rust
use std::thread;

fn main() {
    let a = 100;
    // move 把 a 的所有权移动到子线程
    let jh = thread::spawn(move || {
        println!("{}", a);
    });
    let _ = jh.join();
}
```

**短板**：无法自定义线程名称、栈大小；线程创建失败时程序直接 panic 崩溃，没有自主处理错误的机会。

仓库对应：[1.1-threads-in-rust-move-closure-demo.rs](./1.1-threads-in-rust/1.1-threads-in-rust-move-closure-demo.rs)

### 2. 自定义创建：`thread::Builder`

`Builder` 是 `spawn` 的底层封装：分步构造线程参数，最后调用 `spawn` 创建线程，**创建失败返回 `Result`，不会直接 panic**。

可配置的常用参数：

| 方法 | 作用 |
|------|------|
| `.name("自定义线程名")` | 线程 panic、调试器里可直接看到名字，便于定位出错线程 |
| `.stack_size(字节数)` | 手动设置该线程栈大小；默认由系统分配，只有需要更大栈（深递归等）时才改 |

代码示例：

```rust
use std::thread;

fn main() {
    let builder = thread::Builder::new()
        .name("worker-thread".into()) // 设置线程名
        .stack_size(1024 * 8);        // 栈大小 8 KiB

    // spawn 返回 Result：资源耗尽等返回 Err，不会直接 panic
    let jh_result = builder.spawn(|| {
        println!("自定义配置的子线程运行");
    });

    if let Ok(jh) = jh_result {
        let _ = jh.join();
    } else {
        println!("线程创建失败");
    }
}
```

**适用场景**：批量建线程、需要可读线程名排错、要定制栈大小。

> `thread::spawn` 在标准库里大致等价于 `Builder::new().spawn(...).unwrap()`——方便，但把创建失败变成了 panic。

### 3. 安全借用：`std::thread::scope`（预览，§1.2 完整细讲）

`spawn`、`Builder` 创建的线程都受 `'static` 限制，**不能直接借用**主线程栈上的局部变量。`scope` 用来在**仍借用局部数据**的前提下开子线程。

核心规则：

1. 所有在 `scope` 作用域内部创建的子线程，**一定会在 scope 代码块结束之前全部执行完毕**（作用域结束时会 join）；
2. 编译器可以保证：子线程借用的局部变量，生命周期一定长于子线程运行周期，因此往往**不必 `move`**，子线程能直接借用外层变量。

简易预览（Leakpocalypse、与 `spawn` 对比见 [1.2](./1.2-scoped-threads.md)）：

```rust
use std::thread;

fn main() {
    let num = 50;
    thread::scope(|s| {
        // 无需 move，直接借用 num
        s.spawn(|| {
            println!("{}", num);
        });
    });
    // scope 结束，内部子线程已全部 join 完毕
}
```

## 五、新手易错：`println!` 打印错乱

`println!` 内部会对标准输出加锁，**单次 `println!` 内部的字符串内容不会被其他线程在字节级打断拆分**，但是不同线程先后执行 `println!`，打印的**整行**依旧会互相穿插、顺序混乱。

多线程调试时更稳妥：给线程起名（`Builder::name`）、打印 `thread::current().id()`，或换用带行缓冲的日志库。

## 六、对照：`std::thread::spawn` vs `tokio::spawn`

| | **`std::thread::spawn`** | **`tokio::spawn`** |
|---|--------------------------|---------------------|
| 执行体 | **OS 线程**上跑同步闭包 | Tokio **async task**（Future） |
| 闭包 | `FnOnce() -> T` | `async { … }` → `Future<Output = T>` |
| 句柄 | `JoinHandle<T>` | `JoinHandle<T>`（同名，语义不同层） |
| 等待 | `.join()` **阻塞**当前 OS 线程 | `.await` 挂起 task，**不占用** executor 线程 |
| 约束 | `Send + 'static` | `Future` 须 `Send + 'static` |
| 典型场景 | CPU 密集、阻塞 syscall | I/O 密集、大量并发 |

```rust
// std：sleep 5 秒占住一条 OS 线程
let h = std::thread::spawn(|| { /* blocking */ 42 });
let n: i32 = h.join().unwrap();

// tokio：sleep 时 task Pending，线程可跑别的 task
let h = tokio::spawn(async { tokio::time::sleep(Duration::from_secs(5)).await; 42 });
let n: i32 = h.await.unwrap();
```

**JoinHandle 对比**：std 等的是 **线程结束**；tokio 等的是 **async 任务完成**。
