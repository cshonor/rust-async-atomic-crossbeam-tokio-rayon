## 1. 自旋锁是什么

| 对比 | 行为 |
|------|------|
| **`Mutex`（OS）** | 争不到锁时线程**睡眠**，由内核调度 |
| **自旋锁（Spin Lock）** | 争不到锁时 **忙等**（`while` + `spin_loop`），不陷入内核 |

适用：锁持有时间**极短**、线程数不多、不愿付出上下文切换成本。持有过久会浪费 CPU（书中后文会对比其他锁）。

## 2. 核心结构与内存序匹配

实现见 **`spin_lock.rs`**（与书中逻辑一致，补全 `Guard` + `Deref`）。

```rust
pub struct SpinLock<T> {
    locked: AtomicBool,      // 锁状态
    value: UnsafeCell<T>,    // 被保护数据（需 unsafe 访问）
}
```

| 操作 | API | Ordering | 作用 |
|------|-----|----------|------|
| **加锁** | `locked.swap(true, Acquire)` | **Acquire** | 一旦成功，后续对 `value` 的读写**不能**重排到加锁**之前** |
| **解锁** | `locked.store(false, Release)` | **Release** | 此前对 `value` 的修改**不能**重排到解锁**之后** |
| **等待** | `while swap 仍为 true` + `spin_loop()` | — | 降低自旋功耗；书中强调自旋锁用 **`swap`** 而非在循环里狂 CAS |

### Happens-Before 链条

```text
  线程 1                          线程 2
  写 *value
  unlock: store(false, Release)
                                  lock: swap(true, Acquire) 成功
                                  读/写 *value  // 必见线程 1 的写入
```

**Release（解锁）→ Acquire（加锁）** 建立 HB，从而在**无系统调用**的情况下避免对 `value` 的数据竞争。

### 为何用 `UnsafeCell`

- 多线程共享 `&SpinLock<T>`，不能同时有 `&mut T`。  
- 锁保证「同一时刻只有一个线程」访问 `value` → 在 `Guard` 存在期间用 `unsafe` 解引用是安全的。  
- 需 **`unsafe impl Sync for SpinLock<T> where T: Send`**。

## 4. 选型与易错点（第 4 章视角）

### 与第 3 章选型一致

- 锁标志 **`locked`**：**加锁 Acquire、解锁 Release** — 不要用 Relaxed。  
- 纯统计计数（与 `value` 无关的原子变量）才 Relaxed。

### 本章特有点

| 点 | 说明 |
|----|------|
| **为何 `swap` 而非 CAS 循环** | `compare_exchange` 失败会反复独占缓存行，**缓存争用（Cache Contention）** 严重；`swap` + `spin_loop` 是书中推荐模式（第 7 章再深入） |
| **x86 上仍要写 Ordering** | 即使 x86 硬件强顺序，**编译器**仍可能重排 |
| **Relaxed ≠ 传输慢** | 模型管**顺序**不管**延迟** |
| **勿重复 unlock** | 用 `Guard` RAII；`unlock` 标 `unsafe` 仅内部使用 |

---

## 5. 面试一句话

**自旋锁用 `AtomicBool`：加锁 `swap(true, Acquire)` 忙等，解锁 `store(false, Release)`；Acquire/Release 在锁边界建立 HB，保护 `UnsafeCell` 内数据；标志位绝不用 Relaxed。**
