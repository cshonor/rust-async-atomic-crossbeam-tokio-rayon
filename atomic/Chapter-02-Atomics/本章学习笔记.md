## 1. 内存模型、可见性与数据竞争底层

### 1.1 数据竞争的完整定义（Rust / C++ 底层）

**数据竞争（Data Race）**：**一个线程正在修改某块内存，而另一线程同时在访问（读或写）同一块内存** → **未定义行为（UB）**。

Rust 内存模型进一步强调：对**同一变量**的**并发非原子写入（concurrent non-atomic stores）**即构成数据竞争。

> **区分**：**竞争初始化（Race）** ≠ **数据竞争（Data Race）**。多个线程同时做懒加载、多次 `store` 同一常量结果，可能浪费算力，但若无「非原子并发写普通内存」则不算 DR（见 §2 懒加载案例）。

### 1.2 为何数据竞争会「炸」——编译器与硬件

| 层级 | 行为 | 后果 |
|------|------|------|
| **编译器优化** | 重排、删冗余读写等，**默认不考虑其他线程** | 以为变量不变，实际已被他线程改掉 |
| **CPU / 缓存** | L1/L2、Store Buffer、流水线、**乱序执行** | 写可能暂留本地，**他线程不可见**或**顺序颠倒** |
| **可见性** | 无同步原语时，修改传播无保证 | 结果脱离源码字面逻辑 |

### 1.3 安全并发 vs 不安全并发

| 类型 | 机制 | 数据竞争 |
|------|------|----------|
| **安全并发** | 所有权 + 借用：`&T` 共享 / `&mut T` 排他 | 遵守规则 → **编译期排除 DR** |
| **不安全并发** | `unsafe`、裸指针、`UnsafeCell` 等绕过检查 | 开发者须自证无 DR，否则 **UB** |

**原子操作**的作用：对**单个原子变量**的读/写/RMW 在硬件与语言层面**不可分割** → 该变量上不会出现「非原子并发访问」导致的 DR。

## 2. 第二章精读：原子操作基础

**Atomic（ἄτομος，不可分割）**：操作**要么完整发生，要么不发生**，从而避免该原子变量上的数据竞争。

### 2.1 案例 1：Load 与 Store

| 场景 | 思路 | 本仓库文件 |
|------|------|------------|
| **停止标志（Stop Flag）** | `AtomicBool`；主线程 `store(true)`，后台 `while !load()` | `use_atomic.rs` |
| **进度报告** | 后台 `store` 进度，主线程 `load` 打印；可配合 `park_timeout` + `unpark` 减延迟 | `use_atomic.rs` |
| **懒加载常量** | 初值 0，`load` 为 0 则计算并 `store`；多线程可能重复算，结果相同 → **竞争初始化，非 DR** | `lazy_init.rs`（含不安全版与 CAS 版对比） |

### 2.2 案例 2：Fetch-and-Modify（读改写一条指令）

单次原子指令：**读旧值 + 写新值**（如 `fetch_add`）。

| 场景 | 要点 | 本仓库文件 |
|------|------|------------|
| **多线程进度汇总** | 多线程不能用 `store`（互相覆盖），用 `fetch_add(1)` | `use_atomic_operations.rs`、`use_atomic.rs` |
| **统计 total / max** | `fetch_add`、`fetch_max` 等同变量安全；**多变量之间**仍可能看到中间态（见 §3） | `use_atomic_operations.rs` |
| **ID 分配** | `fetch_add(1)` 发号 | `id_allocator.rs` |
| **溢出回绕** | `fetch_add` 在溢出时 **wrapping**；`u32::MAX` 后变 0 → 安全漏洞；事后 `assert!` **拦不住**其他线程继续加 | `id_allocator.rs` |

### 2.3 案例 3：Compare-and-Exchange（CAS）

**语义**：若当前值 == **期望值** → 写入**新值** 并 `Ok(旧值)`；否则 **不改** 并 `Err(当前值)`。  
`compare_exchange_weak` 可能**虚假失败**（SPARC 等），循环中应使用 weak 版本。

| 场景 | 做法 | 本仓库文件 |
|------|------|------------|
| **防 ID 溢出** | `loop`：`load` → 若超阈值 `panic` → `compare_exchange_weak(id, id+1)`，失败则更新期望值重试；**边界判断 + 更新一体** | `id_allocator.rs` |
| **一次性懒加载（唯一随机密钥）** | 仅 `compare_exchange(0, new_key)` 成功者写入；`Err` 则**丢弃**自己的 key，用他人写入值 | `lazy_init.rs` |

## 3. 日常开发规避数据竞争（实操法则）

### 3.1 优先安全抽象（约 99% 场景）

| 需求 | 优先选用 |
|------|----------|
| 局部并发、可限定线程寿命 | `thread::scope` |
| 共享可变状态 | `Mutex<T>` / `RwLock<T>` |
| 消息传递 | `mpsc::channel` 等 |

**不要**默认手写 `Atomics` + `unsafe`。

### 3.2 必须用 Atomics 时的逻辑陷阱

1. **原子性 ≠ 业务一致性**  
   两个原子变量（如 `num_done` 与 `total_time`）分别 `fetch_add` 时，他线程可能看到「数量已增、耗时未增」的中间态。不可接受 → 用 **`Mutex`** 打包更新。

2. **整数溢出**  
   `fetch_add` / `fetch_sub` **回绕**。全局 ID、索引 → 用 **`compare_exchange_weak` + 循环** 做越界检查与更新一体（Fetch-Update 模式），见 `id_allocator.rs`。

### 3.3 使用 `unsafe` 的底线

- 读文档 **Safety** 段，写清你向编译器保证的不变量（注释在 `unsafe` 块上方）。  
- 记住：**DR 引发 UB** 时，错误影响可被优化器「渗透到」看似无关的前序代码。

## 4. 核心术语（本章 + 跨章）

| 术语 | 含义 |
|------|------|
| **Data Race** | 并发非原子访问同一内存 → UB |
| **Race（竞争）** | 多线程竞态执行，不一定是 DR（如幂等懒加载） |
| **Relaxed** | 单变量原子性，**无**跨变量顺序保证 |
| **Fetch-Update** | `fetch_*` 或 CAS 循环实现的读-改-写 |
| **CAS / compare_exchange** | 期望值匹配才写入 |
| **Wrapping** | 原子算术溢出回绕 |
| **Visibility** | 他线程何时能看到本线程写入（第 3 章用内存序解决） |

## 5. 面试 / 笔试一句话

**Rust 用借用默认消除数据竞争；跨线程无锁共享单变量用原子操作保证不可分割；`Relaxed` 只保单变量原子性；多变量一致性与可见顺序靠 `Mutex` 或第 3 章内存序；`fetch_add` 会溢出回绕，关键资源分配要用 CAS 循环把「检查+更新」打成一体。**
