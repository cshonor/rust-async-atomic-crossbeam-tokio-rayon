# 《Rust Atomics and Locks》第八章 — 操作系统原语

> **本章主题**：支撑 Rust `Mutex` / `Condvar` / 阻塞锁的 **内核与用户态协作**（futex、`pthread`、Windows API）。  
> **不是** Condvar 用法的教学章 — 用法见 [Condvar与条件变量-贯通笔记.md](../Condvar与条件变量-贯通笔记.md)（第 1 章）。

---

## 1. 为什么需要 OS 原语

用户态原子操作在**无竞争**时很快；一旦需要**阻塞 / 唤醒**，必须借助内核：

- 线程进入**睡眠**（让出 CPU）  
- 其他线程在条件满足时**唤醒**等待队列

第 9 章自建锁的 `wait` / `wake_one` / `wake_all` 通常封装本章机制（书中 `atomic_wait` crate）。

---

## 2. Linux：futex

| 操作 | 作用 |
|------|------|
| **FUTEX_WAIT** | 若原子变量仍为期望值，线程休眠 |
| **FUTEX_WAKE** | 唤醒等待该 futex 的线程（一个或多个） |
| **FUTEX_REQUEUE** | 把等「条件变量侧」的线程**重排队**到等「互斥锁侧」，减少 **notify 后全员抢锁** 的惊群 |

两阶段模型：**先在用户态用原子操作尝试**；失败再 **syscall** — 与第 9 章「三态锁」优化一致。

---

## 3. POSIX / macOS

- **`pthread_mutex_t`** + **`pthread_cond_t`**  
- `pthread_cond_wait` / `pthread_cond_timedwait`  
- `pthread_cond_signal` ≈ 唤醒一个；`pthread_cond_broadcast` ≈ 唤醒全部  

Rust 在类 Unix 上常基于此族实现。

---

## 4. Windows

- **`CONDITION_VARIABLE`** + SRWLock / Critical Section  
- 或 **`WaitOnAddress`** / **`WakeByAddressSingle`** / **`WakeByAddressAll`**  

与书中 Windows 锁、RwLock 讨论（SRW 死锁场景）同卷不同章，见 [RwLock与读写锁体系-贯通笔记.md](../RwLock与读写锁体系-贯通笔记.md)。

---

## 5. 与 Condvar / Mutex 的对应

| Rust API | 典型底层 |
|----------|----------|
| `Mutex::lock` 阻塞 | futex / pthread mutex / critical section |
| `Condvar::wait` | 原子释放 mutex + futex wait on condvar 状态 |
| `Condvar::notify_one` | signal / wake one |
| `Condvar::notify_all` | broadcast / wake all |
